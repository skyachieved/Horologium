# AGENTS.md: Horologium

This file is the shared memory of the project. It is written for **AI coding agents and the humans steering them**. Read it fully before changing anything. It is updated at the end of every development phase, never batched at the end.

## What this project is

Horologium is a cross-platform (Windows, macOS, Linux) **floating desktop buddy**: a cute pixel character that sits on top of your screen, moves between menu, icon and hidden with two global hotkeys, and whose menu pops out around it (the open tab is its speech bubble): a Pomodoro timer, a hydration tracker/reminder (counted in cups of water, personalised from your body and activity), a music player, and settings. It has three switchable themes (each with its own voice), English + Korean UI, installers, one-click updates and a News tab.

> **This project is entirely vibe coded.** It was written by an AI agent (Claude) in conversation with its owner, who steers by describing what they want, not by writing code. Treat everything here accordingly: tests are the source of truth, not confidence. If something is unverified it says so below under "Verification status".

## Quick commands

```bash
npm install                  # once (the first `npm start` then downloads the ~100 MB Electron runtime)
npm start                    # run the app
npm test                     # fast unit tests, pure Node, no Electron needed
npm run validate             # load + validate every extension exactly like the app does
npm run test:audio           # render every station in headless Electron and measure loudness/clipping/spectra
npm run test:ui              # drive the real app headlessly with real mouse/keyboard input (25 end-to-end checks)
npm run test:audio -- --calibrate   # ...and print the gainDb that would hit the loudness target
npm run render -- <station> [--seconds 60] [--seed 1] [--out file.wav]   # write a station to a WAV
npm run new -- <type> <id>   # scaffold: theme | character | web-source | locale | station | category | layer | instrument | progression | groove
npm run dist                 # build an installer for the current OS (electron-builder, output in dist/)
```

Node 20+ is required (24 LTS recommended). `npm test` needs no `npm install`: the core has zero runtime dependencies. Electron and electron-builder are the dev dependencies; the one runtime dependency is `electron-updater` (main process only, loaded lazily for self-updating installs; see the 2026-10-29 decision). `package-lock.json` is committed so CI can use `npm ci`.

## Conventions

- **ES modules everywhere** (`"type": "module"`); the Electron preload script is the one `.cjs` exception (sandboxed preloads cannot be ESM).
- **Pure vs impure is a folder boundary.** `src/core/` and any extension's `compose/` folder must not touch the DOM, Electron, the filesystem, or the clock (take `now` as a parameter). That is what keeps them unit-testable.
- **Declarative first.** A new theme, station, or web source is data (JSON/CSS/SVG). Code (`index.js`) is the escape hatch and only for bundled extensions.
- **Every user-facing string goes through the locale tables** (`extensions/locales/en.json` and `ko.json`); a test enforces key parity. Every extension `name` needs both `en` and `ko`.
- **A broken extension must never break the app.** Loaders collect problems and skip the offender.
- No new runtime dependency without a reason recorded in the decision log. Tests use only `node:test`.
- **UI tests use trusted input** (DevTools protocol `Input.dispatchMouseEvent` / `Input.dispatchKeyEvent`). Synthetic `dispatchEvent` skips pointer capture and focus rules; it hid a dead click on the character for a whole release.
- **One-shot animations must call `calm.wake(ms)`** (see `calm.js`): the shell pauses every animation after a quiet spell, so an effect that does not wake the widget would freeze halfway. Theme CSS needs nothing special; infinite animations are paused for it.
- Comments explain *why*, not what. Match the surrounding style.

## Hard rules (do not weaken these)

1. **Terms-of-service guardrails for web music tabs (YouTube, Spotify, Melon, future ones).** Load the service's own site **unmodified**. Never block or skip ads, download or cache audio/video, scrape, automate, inject scripts that change content, rewrite request headers, or spoof the user agent. Stay personal and non-commercial. Show the "unofficial, bring your own account, not affiliated" notice. The web-source contract has **no field** for any of these on purpose; adding one is a policy change that needs the owner's explicit approval. (Source reading: YouTube's developer policies forbid background/audio-only players, separating audio from video, and caching; the YouTube and Spotify terms restrict automated access and circumvention. This is not legal advice.)
2. **No SomaFM-style internet radio presets**: their terms forbid third-party clients.
3. **User-installed extensions are data-only** (JSON, CSS, SVG, audio). They can never contain JavaScript. All inline SVG passes `checkSvgSafety`.
4. **Hydration is general wellness guidance, not medical advice.** Keep the disclaimer in Settings and the README. Clamp targets to 1.2-4.5 L.
5. **Privacy:** the only network calls are weather lookups (city or coordinates to Open-Meteo), the web music tabs the user opens, and the update check (GitHub's latest published release; nothing about the user is sent; Settings > System turns it off; added with the owner's approval on 2026-10-27, see the decision log). No analytics, no accounts.
6. Never spoof or tamper with headers to get around Google's block on sign-in inside embedded views. The fallback is "Open in browser".

- **2026-10-28: "Static" and "monotone" music (item 13): one software artifact found and fixed; songs instead of endless phrases.** *Static.* Measured, not guessed: (a) phrase buffers do NOT click when they end (every buffer ends below -92 dB; now a permanent audio-QA check, "end dB"); (b) **the half-rate render added "fizz"**: stations low-passed at <= 8 kHz render at 22 kHz to save CPU (2026-10-15), and Chromium plays a buffer whose rate differs from the context with linear interpolation, which mirrors the content around 11 kHz. Measured with Chromium itself (the half-rate buffer played through a 44.1 kHz OfflineAudioContext): energy above 14 kHz was -54 to -59 dB of the total versus -86 to -116 dB in a full-rate render of the same phrase, i.e. 30-60 dB of energy the music does not contain, more than these dark stations' own treble. Fix: `render.js` `upsampleClean()` resamples once on the audio thread and strips the images with an 8th-order Butterworth low-pass at 9.5 kHz (four biquads; Web Audio's lowpass Q is in dB): above 14 kHz is now -98 to -152 dB, a permanent audio-QA check (">14k dB", fails above -90 for low-passed stations); cost about +200-400 ms of audio-thread time per ~26 s phrase, still far below rendering at full rate. The engine's new `onRendered` hook calls `window.horologium.collectGarbage()`; the main process runs `HeapProfiler.collectGarbage` on OUR window through the DevTools protocol (attach, collect, detach; at most once per 15 s). - **2026-10-15: An idle widget pauses all of its animations ("calm mode", `src/renderer/js/calm.js`).** Measured in the packaged Linux build (WSL2, software rendering): the collapsed idle widget cost **3.8 % of a core** with the character's two infinite CSS animations running and **0.4 %** with them paused (0.2 % when the compositor was fully idle). Chromium produces 60 frames a second for as long as any animation runs, even if nothing visibly changes, and a 1 Hz DOM tick is nearly free. So after 3 s without interaction (20 s when expanded) the shell adds `.calm` to `#app` and CSS pauses every animation; while collapsed the character wakes for 2.4 s every 20-40 s so it never looks frozen (each pause/resume costs a fixed re-commit, so rarer is cheaper: 12-24 s apart cost 1.4 %, 20-40 s cost 1.1 %). While the widget is hidden it stays calm with no signs of life. Result: collapsed idle **~1.1 %** (90 s window), expanded and left alone **0.3 %** (was 4.7 %). It is theme-agnostic (themes keep writing ordinary infinite animations); the price is the rule that one-shot effects must call `calm.wake(ms)`: the shell does it for drinks, milestones, reminders, phase changes, mood changes, show, hide and expand. A paused pop-out would never finish (the character would vanish instead of leaving), which is why a hide request wakes the widget first. Rejected: `steps()` timing (still ticks at 60 Hz), removing the idle animation (the owner wants a living character), `--disable-gpu` (more CPU, not less). ## How-to recipes

**Add a theme:** `npm run new -- theme my-theme --name "My Theme" --ko "내 테마"`, edit `tokens.css` (all tokens required) and `theme.css`, draw/replace the starter character, `npm run validate`.

**Add a character to a theme:** `npm run new -- character my-char --theme sprout-garden --name "..." --ko "..."`, draw it in `sprite.json` (one character per pixel, keys from `palette`, frames for idle/wave/cheer/sleep), write its lines in `dialogue.json` (EN and KO; situations and placeholders in `docs/extension-api.md`), `npm run validate`.

**Give a theme a voice:** edit the theme's `dialogue.json` (all eight situations, EN and KO); a test requires every bundled theme to cover them all.

**Cut a release:** (1) `npm version <x.y.z> --no-git-tag-version`; (2) add the newest entry to `src/renderer/news.json` (EN and KO; a test checks it matches package.json); (3) update README/AGENTS, run `npm test`, `npm run validate`, `npm run test:ui`; (4) commit, then `git tag v<x.y.z> && git push origin main v<x.y.z>`; (5) `release.yml` builds the installers into a **draft** release; write the notes there (they are what the News tab shows for an available update); (6) the owner publishes the draft. Only then do installed apps see it.

**Add a language:** `npm run new -- locale fr --name "Français"` copies `en.json` with the new `_meta`; translate the values and keep the keys, `npm test`.

**Add a web music source:** `npm run new -- web-source my-service --name "..." --ko "..."`. Read the service's terms first and check them against the hard rules above. Fill `url`, `navAllow`, `partition`. If you need something the schema does not allow (script injection, header changes), stop: that is a policy decision for the owner.

**Add a station (JSON only):** `npm run new -- station sunday-bossa --category lofi --name "Sunday Bossa" --ko "일요일 보사"`. Edit `extensions/music-sources/generated/stations/<id>/manifest.json` (tempo range, keys, which progression banks and groove, voices and their instruments, fx, sliders, presets), then `npm run validate && npm test`, then **calibrate its loudness**: `npm run test:audio -- --calibrate` and copy the suggested `gainDb`. Audition outside the app with `npm run render -- <id> --seconds 60`. A station never touches Web Audio: `compose()` turns its data into a Plan and the engine renders it.

**Add a genre:** `npm run new -- category bossa --name "Bossa Nova" --ko "보사노바"` appends a chip to `categories.json`; a genre needs at least one station (a test enforces it), so add one right away. `custom` (My Stations) is built in.

**Add a sound layer:** `npm run new -- layer cafe-hush` (code, a seamless looping `generate()`) or `--kind noise --color brown` (no code). Reference it from a station's `layers`, then calibrate.

**Add an instrument / chord bank / groove:** `npm run new -- instrument glass-keys --role chords` (or `--role drums` for a kit), `progression <id>`, `groove <id>`. Stations share them by id; the loader checks every reference.

**A personal station (data only, no repo needed):** `npm run new -- station my-vibe --user` creates it in your user folder (shown in Settings > System) under **My Stations**; it can reference any bundled building block but contains no code. Restart the app.

**Add music packs / local music:** drop `<userData>/extensions/music-packs/<id>/manifest.json` + audio files (format in `docs/extension-api.md`); or press "Add folder" in Music > My music. The repo never ships audio. Declare `license` and `provenance` so the pack is not shown as "unverified".

Full field reference: `docs/extension-api.md`.

## Known limitations and open risks

- **DRM:** stock Electron has no Widevine, so DRM-protected full tracks (Spotify, probably Melon, YouTube Premium/Music Premium content) cannot be expected to play in the web tabs. The fallback is "Open in browser" / the service's own app.
- **YouTube Music** redirected signed-out users to a Premium page in South Korea, so it may be unusable there without a Premium account; YouTube proper is the default site. Google may also refuse sign-in in embedded views (credentials not tried); we will not disguise the app to get around it.
- **Ads** play in the YouTube tab (they are never blocked: hard rule 1).
- Generated music is instrumental and algorithmic; the owner judges musicality by ear (agents cannot listen). Automated checks cover structure, loudness, clipping and spectra only.
- **Memory** while a station plays is held near 300 MB only by the explicit post-render garbage collection (`gc.js`); if the DevTools protocol attach ever fails, memory saw-tooths up to roughly 700 MB (it still comes back down).
- **Performance numbers are Linux + software rendering.** Collapsed idle is about 1 % of a core (0.3 % when expanded and left alone), a playing station about 7 %. Windows and macOS are unmeasured.
- Unsigned installers trigger Windows SmartScreen and macOS Gatekeeper warnings; an unsigned arm64 macOS app may need `xattr -dr com.apple.quarantine`. Unsigned macOS apps cannot update themselves (the News tab opens the download page instead).
- **Self-update is unproven end to end** until a release newer than an installed one exists. If it fails, News still offers the release page, and a reinstall over the old version keeps the settings.
- Linux: Wayland global shortcuts need the GlobalShortcutsPortal feature (the tray menu is the fallback); on Ubuntu 24.04+ AppArmor can block Electron's sandbox for AppImages (`--no-sandbox`).
- Windows machines need Node.js installed to clone-and-run (no check here ran with a Windows Node); the installer route needs a tagged release built by CI.

## Rules for agents

1. Read this file and `docs/extension-api.md` first.
2. **Update the decision log whenever behaviour changes**, with why and how it was verified. Update "Verification status" honestly, including what you could not test.
3. Run `npm test` and `npm run validate` before claiming anything is done. Add tests for new core logic.
4. Never weaken the hard rules above. If a request conflicts with one, say so and ask.
5. Prefer a new extension folder over editing core code. If you must edit core, keep it pure and tested.
6. Do not commit, push, or publish unless the owner asks.
